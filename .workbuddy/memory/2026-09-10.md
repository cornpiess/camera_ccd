### 最终打通的路径（可复用）
1. 换节点后，用户代理客户端在 `127.0.0.1:7890` 可用：`curl -x http://127.0.0.1:7890 https://github.com/` → **200**。

     git -c http.proxy=http://127.0.0.1:7890 -c credential.helper= -c credential.helper="$GCM" push origin main

## 15:50 咨询：Expo 账号与 Apple 开发者账号的归属关系

**问题**：两个 Expo 账号能否绑定同一个 Apple 开发者账号？

**结论**：Expo 侧**没有「绑定 Apple 账号」这个动作**。Apple 凭据（分发证书 / 描述文件 / APN key）是在首次 build 或 submit 时按需生成，并存到 **(Expo 账号或组织 + 项目)** 维度上。所以多个 Expo 账号对接同一个 Apple 开发者账号技术上可行，但有两个真实代价：

- **Expo 侧凭据不共享**：账号 A 生成的证书，账号 B 看不到；B 首次 build 时因无私钥只能在 Apple 侧新建一个。
- **分发证书每个 Apple 开发者账号仅 2 个名额**（Expo 官方文档口径；APN key 2 个，描述文件不限量）→ 两个账号各建一个即占满，第三个账号/机器直接卡住。
- 账号间迁移手段：`eas credentials` → `credentials.json` 的 Upload/Download（该文件含分发证书**私钥**，严禁进 git）。

**推荐做法**：建 **Expo Organization**，把两个账号都邀请为 member（Developer 角色即够：能 build、能发 update、能管凭据），项目归属 org（`app.json` 加 `expo.owner`）→ 凭据在 org 内共享，这也是官方对团队协作的唯一推荐方式。

**查证到的项目现状（重要）**：
- 读 `app.json` 确认：**既无 `expo.owner`，也无 `extra.eas.projectId`** → 本项目**尚未与任何 Expo 账号关联**。
- 风险：第一次 `eas build` 会自动创建并认领项目。若两台机器登录**不同** Expo 账号各自 build，会生成**两个不同的 projectId**（双份构建历史 + 两套凭据副本 + EAS 配额算两次）——与代码分叉同级别的灾难。
- **待用户决策**：确定使用哪个 Expo 账号 / 组织，然后把 `owner` 写入 `app.json` 并 `eas init`，纳入开工流程（与 `git pull --rebase` 同级）。

**附带提醒**：`eas submit` 建议用 **App Store Connect API Key** 而非 Apple ID + 2FA——2FA 会话在两台机器上会互相踢下线。

**⚠️ 重要更正**：上一条推荐"建 Organization 共享凭据"**与这个目标直接冲突**。EAS 的 build 配额是**按账号/组织**计的、**不按成员分**——两个账号放进同一个 org 仍然只有一份额度（15 次/月 iOS）。**要两份额度，必须用两个彼此独立的 Personal 账号**，各自持有一个独立 EAS 项目。凭据共享与额度翻倍，二者只能选一个方向。

**官方配额数据（查 expo.dev/pricing 得到）**：

| 项 | Free | Starter $19/mo |
|---|---|---|
| iOS builds/月 | **15**（Android 另算 15） | $45 build credit |
| 并发 | 1 | 1（+$50/个，最多 +5） |
| 队列 | low priority | high priority |
| 单次超时 | 45 min | 2 h |

- 配额按**日历月**，每月 1 号重置。
- **免费额度用完 = 完全不能 build**，不会自动超支计费，是硬墙。
- 官方给出的三条出路：升级 Starter / `eas build --local`（**需 macOS+Xcode，Windows 不可用**）/ 等下月重置。

**双账号翻倍的三个代价**：
1. **projectId 分叉**：`app.json` 的 `expo.owner` + `extra.eas.projectId` 硬编码在代码里，切账号要改 → 会污染 git。需改用 `app.config.js` + 环境变量注入。
2. **分发证书必须共用同一张**：Apple 只给 2 个证书名额，两账号各建一张即占满。做法是 A 账号先生成 → `eas credentials` 导出 credentials.json → B 账号导入并选"使用已有证书"。该文件含**私钥**，严禁进 git。
3. **构建历史与 submit 归属分裂**（submit 可两边共用同一 App Store Connect API Key 缓解）。
- **唯一实质好处**：并发队列分开，两账号可同时跑两个 build（免费队列 low priority 排队很慢，这点很值）。

**合规**：Expo Acceptable Use **无明文禁止**多账号用免费额度；Free Plan 条款为 "at our sole discretion"，可随时调整。本项目属 hobby/POC，符合 Free Plan 适用范围，风险低但非零。

**另一条备选（待用户取舍）**：GitHub Actions macOS runner。**⚠️ 我当场给的 "130+ 次/月" 是错的，已作废**——漏算了 macOS 的 10 倍计费倍率。查证后的真实数字见下节。

## 16:05 更正 + 第三条路：GitHub Actions 的真实额度

**我上一轮的算术错误**：把私有仓库的 2,000 分钟直接除以单次 15 分钟得出"130+ 次/月"，**漏掉了分钟倍率**。GitHub 对 GitHub-hosted runner 的倍率是：**Linux 1x / Windows 2x / macOS 10x**（官方计费文档明确；"使用 1,000 分钟 macOS 会占用账户内 10,000 分钟"）。

**修正后的真实额度（GitHub Free 计划）**：

| 仓库可见性 | macOS 可用额度 | 折算 iOS 构建次数 |
|---|---|---|
| **private** | 2,000 ÷ 10 = **200 分钟/月** | **约 8 次/月**（按 25 min/次） |
| **public** | **不限量**（standard runner 对公开仓库全免费，含 macOS） | 无上限 |

→ **结论：这条路只在仓库为 public 时成立。** 私有仓库下 200 分钟/月 **还不如双 Expo 账号的 30 次/月**。这是本轮最重要的更正。

**新增发现（可能更优）——Xcode Cloud**：
- **Apple Developer Program 会员含 25 compute hours/月**（= **1,500 分钟**，官方页面确认；**无倍率计费**）。
- 超额档位：100 h $49.99 / 250 h $99.99 / 1000 h $399.99。
- 用户**已有付费 Apple 开发者账号**，所以这 25 小时是白给的，且比私有仓库的 GitHub Actions 强 **7.5 倍**。
- 代价：需在 App Store Connect 配 workflow（网页端可编辑，但初次通常仍需 Mac + Xcode）；Expo 项目要靠 `ci_scripts/ci_post_clone.sh` 跑 `npx expo prebuild` 生成 `.xcodeproj`；本机无法验证任何一步。

**当前阻塞点**：需用户决定仓库能否转 public —— 这决定走 GitHub Actions（public）还是 Xcode Cloud（可保持 private）。**未定之前不要动手写 workflow。**

**注**：另有一个 Gitee Go 的说法（个人仓库每月 200 分钟）来自非官方博客，未采信。

## 16:20 落地：GitHub Actions macOS runner CI（用户已选路线）

**用户决策**：仓库转为 **public** → 走 GitHub Actions。理由是 public 仓库的 standard macOS runner 免费且不限分钟，绕开 EAS 每月 15 次 iOS 的硬墙。

**新增文件 `.github/workflows/ios-dev-build.yml`**（仅手动 `workflow_dispatch` 触发，不做 push 自动触发）：

流程：Preflight 校验 → `npm ci` → `npx expo prebuild --platform ios --clean --no-install` → `pod install` → 写 ASC API Key → `xcodebuild archive` → `-exportArchive`（ad-hoc）→ 生成 OTA `manifest.plist` → `gh release create`（上传 ipa + manifest）→ 上传 artifact → 输出 OTA 链接到 step summary。

关键设计：
- **完全不依赖 EAS / Expo 登录态**，因此与 AGENTS.md 红线 1（禁止 `eas build`）零冲突。刻意没用 `eas build --local`，因为红线字面禁止且需 Expo 登录态（本机登录态常失效）。
- **签名走 App Store Connect API Key + automatic signing**，Xcode 自行创建/复用分发证书与 Ad Hoc 描述文件 → 不需要手动搬 `.p12` / 配 keychain（Windows 上做不到）。
- **Preflight 早失败**：缺 secret 或 `bundleIdentifier` 仍是 `com.example.*` 时 30 秒内报错，不白等 25 分钟。
- **OTA 装机**：GitHub Release 托管 ipa + manifest，手机 Safari 打开 `itms-services://` 链接直接装，无需 Mac 或第三方工具。
- manifest 的 bundle id / version / name 从解包后的 `Info.plist` 用 `plutil` 读取，不硬编码。

**本地已验证**（Windows 上可做的部分）：
- YAML 用 `yaml` 库解析通过；14 个 step。
- 11 个 `run` 块全部 `bash -n` 通过。
- 两处 heredoc 经 YAML 块标量处理后结束标记均在行首（无残留缩进）。
- `ExportOptions.plist` 与 `manifest.plist` 用真实 plist 解析器实跑验证可被解析。

**README.md 新增章节** `CI: iOS dev builds on GitHub Actions`，含 4 项前置条件（仓库须 public / 换掉占位 bundleIdentifier / 4 个 secrets / 登记设备 UDID）与装机说明。

**⚠️ 待验证（Windows 上无法验证，必须实跑才知道）**：
- `macos-15` runner 默认 Xcode 版本能否满足 Expo SDK 55 / RN 0.83 要求（workflow 里已打印版本便于排查）。
- `xcodebuild -allowProvisioningUpdates` 配 API Key 能否在 CI 上顺利创建 ad-hoc 描述文件。
- `npm ci` 会按 `package-lock.json` 里锁定的 **npmmirror** 源下载，海外 runner 上的速度/可用性待观察。

### 重要技术发现（已读 node_modules 源码核实，非猜测）
- **`expo.name` 不能写中文**。`@expo/config-plugins/build/ios/Name.js` 的 `setProductName` 走 `sanitizedName()`
  （`ios/utils/Xcodeproj.js:107`），而 `sanitizedNameForProjects` 用 `/[^\W_]+/g` 过滤 —— 中文全被删光，
  回退 `slugify` 同样得不到 ASCII → **最终 `PRODUCT_NAME` 变成字面量 `app`**。
  所以中文显示名只能放到 `ios.infoPlist.CFBundleDisplayName`，`name` 必须保持 ASCII。
- 该覆盖是**官方支持的行为**，不是 hack：`plugins/ios-plugins.js:50` 的 property guard 语义是
  「用户已在 `ios.infoPlist` 里显式设过的键，不再被抽象属性覆盖」，只在构建日志里留一条 warning；
  `withIosBaseMods.js:299` 用 `{...defaults, ...config.ios.infoPlist}` 合并，同样是用户值优先。
- **Windows 上跑不了 iOS prebuild**：`npx expo prebuild --platform ios` 会直接跳过并提示
  "Skipping generating the iOS native project files. Run npx expo prebuild again from macOS or Linux"。
  故 `app.json` 的原生键值在本机只能**弱验证**（`npx expo config --type prebuild`）+ CI 强验证。
  这条已写进 `AGENTS.md` §3。
